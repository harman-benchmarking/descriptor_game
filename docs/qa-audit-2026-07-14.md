# Descriptor Game QA Audit and Colleague Feedback Analysis

**Audit date:** 2026-07-14  
**Project:** Descriptor Game / Descriptor Cards  
**Audited branch:** `main`  
**App package version:** `0.1.0`  
**Requested scope:** inspect the colleague's feedback, perform a full current-game walkthrough, identify faulty logic, bugs, and UI/UX improvements, and recommend what to adopt without changing source code.
**Design-intent revision:** cross-checked against the active product and feature Markdown on 2026-07-14 so documented mechanics are not mislabeled as implementation defects.

## Executive summary

The game has a strong visual foundation and an unusually coherent metaphor for teaching audio descriptors. The colleague's positive observations are accurate: the main navigation is immediately understandable, the art direction is distinctive, the Campus gives the product a clear shape, and the progression from basic cards to composed discoveries is promising.

The colleague's central criticism is also accurate. In its current form, the Atlas often measures exact-recipe guessing rather than listening or semantic reasoning. The most important discovery is that the project already contains much of the richer explanatory copy that the colleague requested. It is either withheld until after the answer is found or blocked by a parser/UI contract defect. This is primarily a disclosure, scaffolding, and feedback problem—not a need to rewrite all content from scratch.

The build should not yet be used for broad learning-validity conclusions. Several confirmed implementation defects can invalidate or misattribute player results:

- Training trials can be submitted and passed without previewing any audio.
- Starting a new blind trial can leave the previous descriptor playing under a newly shuffled A/B/C label.
- Tower can enable scoring before playback has successfully started.

Other verified defects make the experience hard to interpret even when scoring is unaffected:

- Some intended feedback is written only to a `notice` state that is never rendered.
- The card-detail parser does not deliver documented technical rows to the modal.

Separately, the audio/release audit found risks that need targeted render or listening confirmation:

- Reference tracks lack a level-matching manifest, one flavor loop has a measured seam risk pending listening confirmation, and the output path has no final limiter despite large boosts at the default training intensity.

The documentation cross-check materially changes the interpretation of several other findings. Locked Discovery hints, Atlas's semantic recipe-crafting model, full-curriculum Tower entry, current-score-based floor access, Collection dev controls, one-click Lexicon unlocks, Sound Lab conflict stacking, fixed challenge intensity, and the use of a small daily-track family are all documented choices. They may still be poor choices for an external learner build, but they are **design risks or release-configuration questions, not accidental code faults**.

The reported 30-second startup also has credible architectural causes. One all-in-one launcher performs a full asset sync, TypeScript check, and Vite build on every start. Whether that behavior is a product defect depends on which launcher the colleague was given: the project also documents a prebuilt static-server path. The shipped package is dominated by roughly 474 MiB of 1254×1254 PNG runtime icons, including substantial duplicates and stale files. A splash/loading indicator is worth adding, but it cannot hide work that happens before the app process or renderer exists. Preserve the 1254×1254 source masters; derive smaller runtime assets and keep build work out of the external-test launch path.

### Overall verdict

**Promising prototype; not ready for the next external learning-validity round until the confirmed trial/audio defects are fixed and the disputed Atlas/progression design choices are decided explicitly.**

The recommended strategy is to preserve the clean UI and card/region identity, then make the learning loop honest and observable:

1. Require successful listening before an answer can score.
2. Explicitly reaffirm the documented craft-first Atlas or formally revise it into a hybrid ear-training task; then make its instructions and feedback match that decision.
3. If Atlas is meant to teach, surface more of the rich content and feedback that already exists without necessarily revealing exact recipes.
4. Explicitly reaffirm the documented reversible Tower mastery gate or formally revise it to permanent promotion, and define separate internal-QA versus external-player builds.
5. Standardize and validate source tracks.
6. Remove rebuild/extraction and runtime-asset bloat from the supported external launch path before treating a splash as the solution.

## Priority key

| Priority | Meaning |
|---|---|
| **P0** | Fix before the next external learning/QA build. It can invalidate results, lose progression, create unsafe/unfair audio, or seriously block the main flow. |
| **P1** | Fix in the next product-quality iteration. It materially harms comprehension, accessibility, reliability, or maintainability. |
| **P2** | Valuable follow-up after the main loop is valid and stable. |

Priority describes impact, not whether something is a bug. A documented design risk can still be P0/P1 if it undermines the product goal.

| Classification | Meaning |
|---|---|
| **Verified defect** | Current implementation violates active documentation, breaks its own state/audio contract, or fails a normal accessibility/reliability requirement. |
| **Intentional design — reconsider** | Implementation matches the active design, but walkthrough evidence or colleague feedback shows a product/learning cost. Changing it requires a product decision and documentation update, not merely a bug fix. |
| **Release/configuration** | Acceptable in an internal developer/QA build but risky if included in the supported external artifact. |
| **Documentation conflict** | Active or rationale documents point in different directions; ownership must be resolved before implementation. |
| **Unverified technical risk** | Source/file evidence shows a credible failure mechanism, but the user-visible symptom still needs a targeted reproduction or render. |
| **Enhancement** | Useful improvement beyond the current documented contract. |

Findings are marked as **confirmed** when reproduced in the running source build or directly established in source/data/assets. Items marked **hypothesis** or **conditional** require a targeted packaged-app, release-scope, browser, or device test.

## What should be preserved

The following parts are working and should not be lost while addressing the problems:

- The Campus metaphor makes the product's major spaces understandable without a manual.
- The dark visual system, region art, card art, and consistent card grammar create a strong identity.
- Navigation labels and major calls to action are generally clear.
- The gift-pair concept is a good entry scaffold.
- Basic-card detail pages already contain useful sensory language such as “Listen for.”
- The Atlas concept of composing higher-order vocabulary from stable anchors is educationally valuable.
- The craft-first Atlas is deliberately different from Training and Tower; do not accidentally turn every space into the same blind quiz.
- Tower answer reveal can show the correct target and its ingredient cards; that is a useful feedback pattern.
- Sound Lab makes experimentation available outside scored progression.
- Sound Lab's conflicting-card stacks are intentional experiments, and challenge modes' fixed intensity/hidden pre-answer visualizers protect fairness.
- The small gate-specific daily-reference strategy is educationally sound even though the current audio assets need validation and selective replacement/rework.
- Random Integrity events and module-specific visual diagrams are part of the intended perceptual model; lifecycle and reveal bugs should be fixed without flattening those behaviors.
- Preserve 1254×1254 source art masters while generating smaller, deduplicated runtime derivatives.
- The responsive header and single-column layout work reasonably well at 390 px.
- Visible keyboard focus styling is present on major controls.
- The colleague explicitly praised immediate comprehensibility. Do not replace that strength with a mandatory startup tutorial.

## Why the Glassedge/Piercing example fails

The colleague quoted two lines:

- Card front: “Find the stacked edge that feels needle-bright.”
- Locked detail: “A sharp point with no cushion.”

That experience is reproduced exactly. The documentation review confirms that the short locked hint is intentional; the user's failure to learn from it is therefore evidence against the current design assumption, not evidence that the locked-state code failed its specification.

### Root cause chain

1. A locked discovery is rendered as `???` with only its short hint (`web/app/src/ui/components/DiscoveryCard.tsx:21-32`). This matches `app-atlas-region-crafting.md:65-74`.
2. `CardDetailModal` intentionally sets `visibleDetail` to `undefined` for a locked discovery (`web/app/src/ui/components/CardDetailModal.tsx:49-61`). This is the documented reward/secrecy rule, not a parser failure.
3. The project already contains a much better Piercing identity:
   - “The Treble Lance” identity;
   - a feeling describing painful forwardness and missing body;
   - concrete “Listen for” examples;
   - frequency territory, contrasts, recipe notes, and difficulty guidance.
   These are in `web/app/public/docs/descriptor-detail-pages.md:1388-1412` and the source copy.
4. Even after unlock, part of the detail system is broken. `cardDetails.ts` defines fields for frequency territory, EQ move, recipes, contrasts, and difficulty, but its parser only reads rows under `### Player-Facing Identity`. The relevant rows live under `### Technical Details`, so the UI sections at `CardDetailModal.tsx:62-69` can never receive them. This is a genuine implementation/documentation mismatch.
5. Glassedge intentionally presents seven available basics and all twelve locally craftable discoveries at once (`web/app/src/data/regions.ts:64-79`): eight pairs, two triads, one four-card recipe, and one five-card recipe. The active shelf invariant requires that completeness; the ungrouped presentation creates the cognitive-load risk.
6. Piercing requires five exact ingredients: `Thin + Hollow + Shouty + Harsh + Sibilant`. The short hint does not communicate that structure.
7. Locked discoveries have no target-audio preview. Only already-unlocked discoveries can be played (`web/app/src/app/App.tsx:2373-2385`). This matches the documented craft-first Atlas, but it means the player cannot solve “Piercing” by target comparison; target audio would be a deliberate hybrid redesign.
8. The blend evaluator calculates a nearest discovery and contained discoveries (`web/app/src/cards/blendCrafting.ts:57-101`), while the UI renders only the specified status class such as “Close trail,” “Overcrowded,” or “No path” (`web/app/src/app/App.tsx:703-735, 2242-2264`). The current UI meets the active status-level contract; exposing more of the data is a learning-feedback enhancement.
9. Progressive-hint concepts exist in persisted/model state (`hintLevel`, `preferHints`) but no active feature document defines their behavior. They are latent capacity/dead state, not a promised unfinished feature.

The true code defects in this example are the post-unlock detail-parser mismatch and the hidden-name leak below. The short locked copy, complete shelf, exact crafting, and absence of target audio are documented design choices whose learning value should now be reconsidered.

### Concealment defect

The locked name is not actually secure. The info button uses `title="Details: ${label}"`, so hovering it or reading its accessible name reveals “Details: Piercing” while the card itself displays `???` (`web/app/src/ui/components/DiscoveryCard.tsx:28-32`). This is both a gameplay spoiler and an accessibility-equity problem.

### Recommended locked-discovery design

For a learning-first Atlas, the locked detail should reveal:

- target name, unless mystery itself has a proven learning benefit;
- a plain sensory definition;
- two or three “Listen for” examples;
- a contrast such as “not Fatiguing because…”;
- recipe size (“uses 2 cards,” “uses 5 cards”);
- optional progressive hints based on attempts.

It can still hide:

- the exact ingredient names;
- the exact EQ/filter recipe;
- the final icon/art reward.

If the name must remain hidden, the modal still needs enough semantic information to reason: the number of ingredients, audible dimensions, and staged family hints. The current two poetic sentences are not sufficient.

### Optional hybrid Atlas learning loop

1. Select one discovery mission rather than viewing twelve equal mysteries.
2. Read the short definition and listening target.
3. Play the hidden target sound.
4. A/B between target and selected candidate blend.
5. Submit a blend.
6. Receive structured feedback such as “2 of 3 ingredients match,” “one extra card,” or “correct brightness family; missing body cue.”
7. After repeated attempts, reveal a stronger hint according to the existing hint preference.
8. Unlock the full identity, ingredient map, contrast examples, and icon.
9. Revisit it later in a blind mastery task.

This would retain discovery and satisfaction while turning failure into instruction, but it is a product pivot. If Atlas remains craft-first, keep target-audio exams in Tower and instead add semantic mission tiers, recipe-size cues, grouped shelves, and richer near/extra/missing text. Either direction is coherent; the current mixture is not sufficiently self-explanatory to the tested learner.

## Full walkthrough findings

### 1. Startup and launch

#### What works

- Electron uses sensible baseline isolation settings: context isolation on, Node integration off, and sandbox on.
- The app has a dark background color, so a renderer delay does not flash white.
- The local browser launcher provides understandable console messages when Node or dependency installation fails.

#### Confirmed observations and conditional release issues

- `web/Start Descriptor Game.bat:27-40` intentionally acts as an all-in-one source launcher and performs a full build before starting the server. This is a developer convenience; it becomes a release fault only if it is the supported colleague entry point.
- On that path, the build's prehook re-syncs assets, Vite copies the full public tree again, and the launch can write approximately **949 MiB** before the user sees the app.
- The first source-launch run may also install a roughly **764 MiB / 13,620-file** dependency tree.
- Browser launchers open the URL before confirming the server is listening, so a connection-refused page can race the server.
- Electron shows an empty renderer/root over a background and does not handle `loadURL`, `did-fail-load`, `render-process-gone`, or `unresponsive` with a user-facing recovery surface.
- The local server returns `index.html` with HTTP 200 for a missing JS/image/audio path, masking deployment errors as browser MIME/parse failures.
- The active technical docs describe a static web build but do not define the Electron/local-launcher distribution stack or supported platforms. There is also no build identifier to connect colleague feedback to a precise artifact. These are release-governance gaps rather than gameplay defects.

#### Asset/package evidence

| Inventory | Measured size/condition |
|---|---:|
| `public/` | 512.41 MiB |
| `dist/` | 512.79 MiB |
| Packaged `app.asar` | 512.85 MiB |
| Portable EXE | about 591 MB decimal / 563.3 MiB |
| Setup EXE | about 591 MB decimal |

The application logic is not the package-size problem; runtime artwork distribution is. The 1254×1254 format is intentional for source/master art. Some exact duplicates are also deliberate placeholders or reused art, so the duplicate count is a storage opportunity, not 55 content defects.

#### Adoption decision for the loading suggestion

Add a boot/loading/error surface, but sequence the work correctly:

1. Define the supported external-test artifact; do not rebuild during that artifact's launch.
2. Prefer a prepared installed artifact for testers.
3. Preserve source masters, generate display-sized runtime derivatives, and remove unnecessary duplicate/stale runtime copies.
4. Measure installed, portable, and developer-launch cold/warm timings separately.
5. Then add immediate native/static startup feedback and a failure/retry state.

### 2. Campus and Orientation Center

#### What works

- Campus tiles communicate place, status, and purpose well.
- Orientation explains the main path and separates tools from progression.
- Locked Lexicon and Tower tiles explain their prerequisites.
- The main path is visually memorable.

#### Problems

- The app marks untouched curriculum stages “In progress”; the docs do not define a “Not started” state, so this is a status-language enhancement/clarity risk rather than a specification violation (`web/app/src/app/App.tsx:2530`).
- Atlas is intentionally shown as step 2 and its locked regions intentionally do not open. Each tile already displays `Unlock all basics`; the defect is that it remains an enabled button whose click provides no additional response.
- The global `notice` intended for lock feedback is never rendered.
- Internal screen changes do not restore scroll position. This was reproduced by clicking a below-fold “Start training” action: Training opened at approximately `scrollY=482`, hiding its hero and lane controls above the viewport.
- The header eyebrow always displays the Thunderstep summary “Impact, energy, and spark,” regardless of the current screen (`web/app/src/app/App.tsx:1121-1123`). This reads like a dynamic context label but is a hardwired region string.
- Useful Orientation strings for purpose, method, outcome, and the basic loop exist in `en.json` but are not rendered. They are dormant copy that could support contextual guidance, not proof of a broken requirement.

#### Recommendation

- Keep Orientation lightweight.
- Add a clear “Not started / In progress / Complete” status model.
- Keep Atlas visible early as designed, but make locked tiles unambiguously disabled with prerequisite text or open a deliberately specified preview/CTA.
- Restore scroll/focus to the new screen heading after internal navigation.

### 3. Training Grounds

#### What works

- Gift pairs provide an approachable semantic contrast.
- The target descriptor and its summary are visible before a blind trial.
- A/B/C labels hide the descriptor names until answer reveal.
- A successful/failed answer reveals option labels visually.
- Gate-specific default-track metadata exists.

#### Validity defects and feedback gaps

1. **Answers can be submitted without hearing anything.** Every “Choose A/B/C” button is enabled before preview (`web/app/src/app/App.tsx:1754-1786`). A player can unlock a target through a 1-in-3 guess.
2. **A new trial can retain stale sound.** “New trial” only recreates local trial state. It does not pause audio or clear the app-level `blindPreviewState` (`web/app/src/app/App.tsx:1706-1710, 1792-1795`). Because active preview identity is matched only by gate, target, and A/B/C label, the new A can appear active while the descriptor from the old A is still playing.
3. **Playback failure is not represented.** Preview play promises have no error UI or cancellation. A stale promise can complete after navigation or a rapid switch.
4. **P1 feedback/accessibility gap: correctness feedback is not textual.** The UI relies heavily on green/red styles. Translation keys for explicit correct/not-yet text exist but are unused, and relevant notice paths are not rendered.

#### Additional issues

- `previewedLabel` stores only the most recently previewed label. After hearing A and then B, A can return to “Not previewed.” This wording is misleading, but a full preview set becomes functionally required only if the product adopts an all-options policy.
- Starting a new trial before submission is not forbidden by the design; the defect is that it does not reset parent/audio state atomically.
- All modules and gates are exposed immediately. This is consistent with the documented explorable-course principle, but a recommended-next highlight could add progressive disclosure without removing freedom.
- The default carriers are intentionally the `daily-*` files; official tracks deliberately have no gate suitability. The issue is that the current daily assets do not fully satisfy the planned naturalness, completeness, level-matching, and perceptual-validation brief.
- A wrong selection still reveals option labels visually, but its richer notice/contrast feedback path is invisible.

#### Recommendation

- At minimum, do not score until one preview has successfully begun; this is the documented listen-then-choose contract. Requiring all A/B/C options once may be a useful beginner policy, but it is a new product rule that should be tested rather than assumed.
- Track preview state per trial ID and per option.
- Starting a new trial must pause old audio, clear global preview state, create the new mapping, and reject stale async completions.
- Add explicit feedback and one actionable listening cue after a wrong answer.
- Consider two challenge layers: broad frequency-region discrimination first, fine within-band discrimination later. This aligns with the existing `docs/JNS_comment.md` analysis.

### 4. Listening Atlas

#### What works

- Regions are understandable perceptual groupings.
- Basics and discoveries share a consistent card language.
- Exact recipes and near/overloaded/miss states are deterministic and unit-tested.
- Successful crafting provides a satisfying visual reveal.

#### Documented design risks and actual defects

- Region locking is intentional; the actual defect is enabled-looking, silent locked controls.
- Locked discovery names and rich identities are intentionally withheld, and target audio is not part of the current craft-first contract. The colleague's confusion makes this a validated design risk.
- The info-button title leaks the hidden name.
- The UI shows the currently specified status class but leaves richer nearest/contained evaluator data unused.
- Hints remain generic after multiple failures; persisted hint-related fields exist, but no active progressive-hint behavior is specified.
- Blend history and unique-attempt progression are session-only and disappear on reload/navigation state reset. Persistence is not promised by the active docs, so this is an optional learning-analytics enhancement.
- Conflicting cards can be automatically removed, but the explanation is written only to the invisible notice.
- Glassedge's complete seven-input/twelve-target shelf is intentional under the exhaustiveness invariant, but its ungrouped presentation creates excessive cognitive load.
- The shelf does not visually group pair, triad, four-card, and apex discoveries.

#### Recommendation

- Stage or visually group each region by tier and mission while preserving the complete-shelf invariant.
- If Atlas evolves into a hybrid ear-training mode, add target audio and A/B comparison; otherwise keep that exam behavior in Tower and strengthen semantic crafting cues.
- Specify a progressive-hint policy before implementing the latent hint settings/model fields.
- Render near-match information without immediately exposing exact recipes.
- Decide whether the documented semantic crafting Atlas should evolve into a guided listening/crafting hybrid in response to this feedback, and make the UI promise explicit.

### 5. Collection

#### What works

- The module grouping is consistent with the curriculum.
- Locked/unlocked art creates a collection incentive.
- Detail modals connect basics, discoveries, and aliases.
- “Use in Sound Lab” is a useful bridge from reference to experimentation.

#### Internal-design features and product gaps

- Collection intentionally contains `Dev: get all basics`, `Dev: get all discoveries`, `Dev: get all aliases`, and `Dev: wipe save` for internal iteration (`web/app/src/app/App.tsx:3013-3025`). Their existence and location are not defects.
- There is no defined build-mode separation or badge. If these controls were present in a player-facing colleague artifact, they could invalidate progression data and make screenshots/results impossible to interpret.
- Wipe/reset has no confirmation or undo. This is a safety enhancement to a documented destructive action.
- The full catalog is very long and has no search, filter, “new,” or incomplete-only view.
- Locked basics/Discoveries intentionally make both primary click and detail action inspectable. Only the hidden-name title leak is a defect.
- Basic/Discovery summaries are suppressed in the grid. The active docs promise them in detail views, not necessarily on every tile, so richer grid copy is an enhancement.

#### Recommendation

- Define internal-QA and external-player artifact modes. Preserve the tools in QA mode; compile/feature-flag them out of external mode and label QA mode visibly.
- Require explicit destructive confirmation for reset.
- Add module/type/status filters and search after the main-loop fixes.
- Add a build/QA-mode badge when developer controls are intentionally enabled.

### 6. Lexicon Hall

#### What works

- Alias cards connect informal listener language to stable anchors.
- Context prompts and explanations are directionally strong.
- The exercise reveals the selected anchor and allows another try.

#### Documented choices and actual gaps

- Entry intentionally requires all 49 Atlas discoveries. This delays useful vocabulary transfer until very late and is a curriculum-design risk, not an implementation bug.
- One correct click intentionally unlocks an alias. The shallow mastery rule and lack of graduated wrong-answer reasoning are design limitations.
- Each alias currently has exactly one live context by specification; an array-capable model does not make this a defect.
- Re-practicing an already-unlocked alias can still use the “unlocked one” success copy.
- Like other modals, alias detail has no Escape handling, focus trap, initial focus, focus restoration, or background inertness.

#### Recommendation

- Consider changing the documented access rule to module/smaller Atlas milestones so Lexicon can reinforce vocabulary earlier.
- Decide whether one correct mapping demonstrates acquisition or only first exposure.
- Add contrast explanations after wrong choices; add and rotate contexts only after the content/spec supports more than one live context.

### 7. Sound Lab

#### What works

- Free mix, intensity, track selection, and module visualizers make it a useful experimentation tool.
- The eight-card limit is stated in the interface.
- Active cards are indicated and removable.

#### Gaps and enhancements

- In a completed save, all 49 learned basics form one long stream without module filters or search. This is a P2 enhancement, not a contract violation.
- Reaching the eight-card limit silently rejects the ninth selection because the corresponding notice is never rendered.
- Source-track levels vary substantially, making cross-track “same settings, different song” comparisons and user volume behavior inconsistent. Within one A/B/C trial, all options use the same carrier, so corpus-level RMS spread does not itself reveal the answer.
- Placeholder wording leaks into several image alt strings.
- At 320×568, the Sound Lab produced a small horizontal overflow/scrollbar (about 6 px); Campus did not. This is a defect only if that viewport belongs to the supported web/mobile matrix, which is currently undefined.
- Electron enforces a 1024×700 minimum size, so narrow responsive layouts are web-only under the current shell. That can be deliberate once platform/viewport support is documented.

#### Recommendation

- Render the limit/conflict notice inline.
- Add module tabs/filtering and a selected-card tray.
- Keep user-uploaded files here as an unscored, local/session feature after audio error handling and level guidance exist.

### 8. Calibration Tower

#### What works

- Floors express a clear mastery ladder.
- Answer reveal can identify the correct descriptor and its ingredients.
- The score system supports partial credit on later task types.
- Floor-specific prerequisite data already exists.

#### Documented progression choices and implementation defects

1. **Documented live-score access:** Floor access is recalculated from the current score of every prior floor (`web/app/src/app/App.tsx:407-413`). A learner can reach 8 points, enter Floor 2, then fall to 7 and relock it after a later Floor 1 error (`App.tsx:809-826`). This matches `app-calibration-tower.md:104-133`; whether “promotion” should instead be permanent is a product decision.
2. **Documented cumulative score:** Continued correct practice can display values such as `24/8` because the spec defines a minimum but no maximum. This is not a scoring bug, although the slash presentation looks like overflow rather than “score / promotion threshold.”
3. **Verified defect — preview is marked complete before playback succeeds.** `previewed` becomes true before the awaited play call returns (`App.tsx:798-806, 891-900`), so a decode/play failure can still enable scoring controls, contrary to the documented play-before-answer sequence.
4. **Verified defect — Floor 3/4 visual feedback remains hidden.** The visualizer hides while `selectedId` is empty (`App.tsx:533`), but ingredient-recipe floors submit `selectedIngredientIds` without setting `selectedId` (`App.tsx:834-855`). The design hides visuals before submission but intends answer analysis afterward.
5. **Documented completionist entry:** Tower requires all 49 basics, all 49 discoveries, and all 16 aliases—114 unlocks. This matches the Campus curriculum spec but conflicts with the broader fairness-only prerequisite principle and duplicates per-floor basic requirements.
6. **Documented score floor:** Feedback can say “-1 point” at zero while stored score remains zero. That describes the attempted result under a minimum-zero rule; showing the actual net change would merely be clearer.

#### Recommendation

- Decide explicitly between a reversible current-mastery gate and permanent promotion. If permanent, persist a high-water flag separate from practice score; if reversible, rename/explain it so relocking is not a surprise.
- Consider separating lifetime score/accuracy, promotion progress, and access state so `24/8` has an unambiguous meaning.
- Enable answers only after successful playback start.
- Model submitted state consistently across floor types.
- Revisit the active global entry rule against the fairness-only principle and research rationale; floor-specific prerequisites are a proposed curriculum change, not the present contract.

### 9. Settings and localization

#### What works

- Locale selection persists locally.
- Reset is easy to find.
- Settings is visually simple.

#### Incomplete/conditional features and real gaps

- The reset action is documented, but whether it should be immediate and whether it needs confirmation/undo are unspecified. The current one-click behavior is a safety/specification gap, not a violation of an explicit interaction rule.
- The language picker advertises four languages, but English has 772 keys while German has 7 and Japanese/Chinese have 6. Historical rationale explicitly deferred English-only Lexicon content, not the whole application's locale coverage; advertising four mostly untranslated global locales still creates a false affordance.
- Live testing Japanese produced a mixed-language Settings/audio screen rather than a translated app.
- The rich detail Markdown is English-only.
- `<html lang="en">` never changes with the selected locale. This is a genuine accessibility/localization defect whenever locale selection is offered.
- `reducedMotion` and `preferHints` are persisted but not exposed or consumed. They are latent/dead state; active feature docs do not promise controls or behavior. Independent support for `prefers-reduced-motion` is still an accessibility gap.
- Focused feature docs intentionally place intensity only in Sound Lab. High-level Campus/gameplay summaries that still place it in Settings are documentation drift.

#### Recommendation

- Until a locale reaches an agreed coverage threshold, label it “preview” or hide it in external builds.
- Add automated translation-key coverage checks.
- Update the document language dynamically.
- Implement and expose reduced motion and hint preference, or remove the dead settings until ready.

### 10. Accessibility and keyboard behavior

#### Confirmed gaps

- Card and alias dialogs do not move focus into the modal, trap focus, close on Escape, restore focus, or make background content inert.
- During the live modal test, focus remained on the background details trigger.
- Correct/wrong blind-answer state is primarily color/style based and is not live-announced.
- The unused global notice prevents many errors and status changes from being announced.
- Playback mode buttons use selected CSS classes without `aria-pressed`.
- Active navigation uses CSS state without `aria-current`.
- Several accessible labels are hardcoded English.
- Locked discovery accessible/title text leaks the answer.
- Saved reduced-motion preference is ignored and no `prefers-reduced-motion` fallback is present.

#### Recommendation

- Treat accessible modal behavior and live task feedback as P1 release criteria, not visual polish.
- Make locked content equally informative and equally concealed for sighted, keyboard, and screen-reader users.

## Audio and reference-track analysis

### Clarifying “AI-generated”

The colleague's wording is understandable, but the four `daily-*` carriers are procedurally generated by `web/tools/node/generate-learn-audio.mjs`. The “spoken voice” is synthesized from oscillators, formants, and noise. The active docs retain the daily-reference strategy but no longer state all asset acceptance criteria; the archived/absorbed track brief specifically requested a natural podcast/tutorial voice and level-matched sources.

The useful conclusion is not “AI is bad.” It is that the primary learner-facing carriers have not been validated as natural, diagnostically appropriate program material.

### Approximate source-level audit

These are simple full-file 16-bit PCM RMS measurements, not a replacement for LUFS and true-peak analysis:

| Track | Approximate RMS |
|---|---:|
| Shadow | -11.9 dBFS |
| Fragments of Time | -12.5 dBFS |
| No Sanctuary Here | -13.9 dBFS |
| Daily drum and bass groove | -17.9 dBFS |
| Daily acoustic pop | -20.0 dBFS |
| Daily piano and guitar | -23.5 dBFS |
| Daily spoken voice | -30.1 dBFS |

The full listed corpus spans approximately 18 dB, while the four daily carriers themselves span roughly 12 dB. This can influence perceived detail, cross-gate difficulty, cross-track comparisons, and user volume behavior. It does **not** directly leak the correct answer inside one A/B/C trial, because all options in that trial process the same selected carrier. The engine has one shared master trim and no per-track normalization metadata.

All nine WAVs parse as stereo 16-bit PCM. File validity is therefore not the same issue as suitability.

### Headroom risk

The official tracks already approach full scale. The default training intensity is intentionally 200% so early learning differences are exaggerated; that rule should not be “fixed” by making the cards inaudible. At the audit baseline, several descriptors applied large boosts while the final master connected directly to the destination without the final safety ceiling already acknowledged as deferred prototype debt in the module docs. A read-only RBJ peaking-filter simulation matching those settings predicted post-master sample peaks of approximately:

- Shadow: +5.19 dBFS;
- No Sanctuary Here: +3.32 dBFS;
- Fragments of Time: +5.25 dBFS.

This is strong evidence of clipping risk. The approved remediation pass added the final shared limiter/emergency sample ceiling. Exact browser/offline reconstructed true peak still needs the automated maximum-stack render matrix, so release verification for QA-009 remains open; carrier loudness calibration is P1 unless standardized cross-track scoring is in scope.

### Recommended track policy

1. Preserve the intended small, plain, gate-specific reference strategy; commercial songs should supplement or replace individual carriers only when they improve diagnostic suitability.
2. Ask Schneider for candidate rating tracks and proof of distribution rights.
3. Blind-evaluate each candidate by gate and descriptor; do not accept it only because it is a commercial/real song.
4. Define a preprocessing manifest containing source, license, edit, duration, loop points, channel layout, LUFS, true peak, and approved gates.
5. Level-match accepted material and check that exaggerated EQ training cannot exceed the chosen output ceiling.
6. Keep procedural carriers as deterministic development fixtures if they remain useful for tests.
7. Complete the missing specialist carriers for serious Spatial/Integrity testing or explicitly document the current fallback phase.

### User uploads

Recommended scope: **Sound Lab session mode first**.

Required design decisions:

- local-only privacy statement;
- supported formats/codecs;
- file-size and duration limits;
- decode/loading/buffering/error UI;
- object-URL cleanup;
- whether files persist across sessions;
- level guidance or analysis;
- no use in standardized scores unless the mode is explicitly marked non-comparable.

Do not make upload the substitute for a curated standard corpus.

## Curriculum recommendation

The active Campus/Orientation specification intentionally uses completionist gating:

- 49 basic cards;
- 49 discovery cards;
- 16 alias cards;
- 114 total unlocks before Tower.

This is not an implementation fault. It is a product decision that appears too strict for a learning path, conflicts with the principle that prerequisites should protect task fairness, and differs from the earlier Tower research rationale. Tower declares required basics per floor, but replacing the global gate would also require explicit per-floor Discovery/alias-vocabulary prerequisites where the answer set depends on them. Changing the rule requires coordinated product-document, UI, and test updates.

Recommended split:

| Layer | Purpose | Suggested access rule |
|---|---|---|
| Core Training | Learn broad anchors and basic contrasts | Guided gate progression with optional free navigation. |
| Core Atlas | Apply anchors to small recipes | Pair missions first; unlock a small module milestone. |
| Lexicon reinforcement | Connect listener language to anchors | Open per module after several relevant basics/discoveries. |
| Tower mastery | Scored blind practice | Proposed: each floor opens from its own vocabulary prerequisites; separately decide reversible mastery versus permanent promotion. |
| Completionist collection | All 114 cards, advanced/apex recipes | Optional achievement, not a baseline gate. |

This proposed split preserves the large vocabulary while reducing the newcomer's working-memory burden. It should be treated as an alternative curriculum model for discussion, not as the bug-fix acceptance condition.

### Wave 0 — make QA results trustworthy

- Enforce successful preview before Training/Tower scoring.
- Fix the stale “New trial” preview/audio mapping.
- Explicitly reaffirm the documented reversible Tower gate or formally revise it to permanent promotion; then separate/label threshold, cumulative score, and access state accordingly.
- Render all important notices and audio errors.
- Define internal-QA versus external-player builds; guard dev controls only in the external mode and confirm destructive reset.
- Add a final audio safety ceiling and offline maximum-intensity tests.

### Wave 1 — respond to Atlas learning feedback

- Decide whether the craft-first Atlas remains semantic or becomes a listening/crafting hybrid.
- Expose useful locked-state definitions/cues to the extent allowed by the chosen mystery rule.
- Fix detail parser/schema coverage.
- Add target audio and A/B comparison only for the hybrid direction.
- If the active Atlas contract adopts richer diagnostics, surface structured near-match feedback.
- Specify progressive hints before implementing the latent settings/model.
- Guide/group pair -> triad -> advanced/apex recipes while preserving the complete-shelf invariant unless that invariant is intentionally changed.
- Remove the locked-name tooltip/accessibility leak.

### Wave 2 — standardize program material and startup

- Preserve the gate-specific daily-reference strategy while validating/replacing weak assets and licensing suitable Schneider candidates.
- Calibrate loudness and validate true peak and loop seams for every accepted carrier.
- Keep current procedural sources as test fixtures if they cease to be primary learner content.
- Make audio scheduling suspend/cancel-safe and validate discontinuity-free graph updates while preserving intentional random Integrity behavior.
- Stop rebuilding on the supported external launch path; the internal source launcher may remain.
- Preserve 1254×1254 masters; generate right-sized runtime art, deduplicate unnecessary copies, and prune stale runtime assets.
- Start the server before opening the browser on supported local-launcher paths.
- Add boot, fatal-load, and recovery UI.
- Add artifact version/build identity.

### Wave 3 — accessibility, reference usability, and breadth

- Implement accessible modal behavior and explicit text/live feedback.
- Honor reduced motion and synchronize document language.
- Either complete translations or mark/hide preview locales.
- Add Collection/Sound Lab search and filters.
- Fix small-screen overflow and decide real mobile/PWA support.
- Add session-only user upload in Sound Lab.

## Documentation drift found

The following inconsistencies should be addressed during the later standardized-development-flow discussion:

- Product name varies among “Descriptor Playground,” “Descriptor Cards,” and “Descriptor Game.”
- `descriptor-gameplay-rules-and-concept.md` lists Glassedge content that does not match `regions.ts`.
- Gameplay and technical source-of-truth docs list only Tower Floors 1–3 while focused Tower docs and implementation have six.
- Gameplay docs place intensity in Settings, but the UI exposes it only in Sound Lab.
- Collection documentation and detail rendering behavior disagree.
- Campus explicitly requires full-path Tower entry, while the broader gameplay principle says prerequisites should exist only for fairness and the earlier Tower rationale recommends access after spectral basics.
- The active track policy keeps the daily-reference direction but omits naturalness, level-matching, and completeness criteria from the absorbed rationale; two specialist daily carriers remain absent.
- The technical source documents a static web build but does not own the Electron shell, local launcher behavior, supported platforms, or internal-QA versus external-player artifact contract.
- Active source, `dist/`, and packaged release artifacts differ without a visible build ID.
- Track tests validate mappings/presence, not audio quality or suitability.

This pattern supports a later definition-of-done that includes source-of-truth updates, content-schema validation, audio/asset QA, accessibility, packaged-startup measurement, and a clean-save end-to-end playthrough.

## Final assessment

The colleague has identified the right product problem, but the design cross-check changes the diagnosis. Atlas is behaving substantially as specified: a craft-first mystery system that withholds identity until exact discovery and provides status-level feedback. The test shows that this documented model is not teaching the sampled learner effectively in its current Glassedge presentation. Withheld locked copy, no target audio, and the complete shelf are design choices to validate or revise; the parser failure, hidden-name leak, and silent feedback paths are actual bugs.

The best next build should be narrower, not larger: fix the verified trial/audio/detail/accessibility defects; decide Atlas and Tower semantics before changing them; preserve but validate the small daily-reference strategy; and give the tester a named, traceable prebuilt artifact. Preserve the art direction and directness that already made a strong first impression.
